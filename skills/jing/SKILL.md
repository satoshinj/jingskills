# jing:主入口与路由

jingskills 是内容生产与相关咨询的工具箱。用户可把这类任务交给 `/jing` 选择成员技能或执行已授权管线；一般办公、编程及无关任务不由本入口接管。

**路由哲学（默认单步，明确终点时连续执行）**：需求只有处境或下一步不稳定时，只决定当前一步。用户已明确终点时，优先复用稳定交接协议；缺少正式模板时，主控整理最小输入、输出、约束和验收条件后继续已授权工作，不因缺模板停止。保留明确的用户确认门，不把正常交接变成逐段审批。内容管线的固定终点是已验证草稿；公开发布不属于这条管线，也不能从“推送”“发布流程”或过去的许可中推断。

## 怎么分发

1. 读当前对话已有的信息(处境、目标、材料、卡点)。
2. 对照下面的路由表,判断意图落在哪条线、哪个 skill。
3. 默认只选一个 skill，说明为什么是它，然后按那个 skill 的 SKILL.md 执行。若用户明确要求端到端内容生产，读取 [content-pipeline.md](references/content-pipeline.md)，按阶段门控连续调用 `jing-writer`、`jing-cover`，再按目标平台调用 `jing-wechat` 和／或 `jing-x-article`。
4. 信息不足以判断时只问一个最关键的问题；正常的阶段交接、验证和可恢复重试不反复打断用户。

## 平台动作先分级

调用平台 Skill 前读取 [平台授权与确认](references/platform-authorization.md)，按当前任务完整对话判定 `local_only` 或 `draft_write`。同一任务的有效许可覆盖正常续做；公开发布不属于管线。公众号两道门按该文件执行，已确认事项不重复询问。

## 常见衔接(供判断下一步)

这些不是固定流水线,是"上一个结果出来后,通常接哪个"的经验参考:

- `jing-consult` 诊断段出了结论 → 通常直接进方案段;若结论是红灯,方案的 Phase 0 就是补齐前提。
- 任何一段实战(上线/排障/事故处置)完成 → 可接 `jing-writer` 的 thread 骨架模式把它变成内容。
- 用户没有兼容的本地知识库、但希望内容长期积累 → 先接 `jing-obsidian` 安全初始化，再把根目录和材料交给 `jing-writer`。
- `jing-writer` 完成并通过事实、语气与移动端可浏览性检查 → 接 `jing-cover` 生成平台封面；需要进入公众号草稿箱时接 `jing-wechat`，需要进入 X 后台时接 `jing-x-article`，两者默认只保存草稿。用户明确要求“走完整条管线”时按 [content-pipeline.md](references/content-pipeline.md) 连续执行。
- 已核验长文要做一次素材多次分发 → `jing-writer` 进入口播再分发模式，生成绑定母稿指纹的口播内容包；需要拼贴 B-roll 时再接 `jing-broll`。图片长文只在用户明确要求时进入后续视觉阶段。
- 清晰的大体量任务、关键复核或 X / Reddit / 网页实时调研 → 可接 `jing-multimodel`,由当前主控选择最小充分的外部通道并验收。

## 边界与纪律

- **只做路由和阶段编排，不替代成员 skill 的判断**。单步任务交给一个成员；端到端内容任务按交接协议串联成员，不在主路由里临时改写成员规则。
- **内容类不虚构**：`jing-writer`(含 thread 骨架模式)不得编造作者经历、数据或情绪。整篇内容属于别人时走译介模式，靠授权和署名解决，不靠改写规避；`source_permission` 没放行的译稿只做本地产物。
- **草稿与公开发布严格分开**：`jing-wechat` 和 `jing-x-article` 的完成状态都是已验证草稿；任何白名单、出口 IP、登录或文件共享权限的修复都不能扩大原授权。
- 一个请求只是顺带提到多条线时，选**此刻最该做的一步**；用户已明确要求的多个成果由主控持续完成，不把其余成果降为可选“下一步”。成员 Skill 的“退回”表示主控在原授权内修正并重验；真正缺少必需信息、权限或能力时，暂停依赖步骤并继续其他工作。
